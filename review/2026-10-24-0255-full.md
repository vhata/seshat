## Summary

Eight open findings: two P1, five P2 and one P3. Seven are promoted
to separate review-backlog work; callback rate limiting is already queued.
The most consequential failures are in continuation lifecycle and ordering:
an orphan continuation can stop event reads, and a continued sweep can
replace newer event data while reporting a successful sync. Other findings
affect owner changes, monitoring consent, CLI exclusions and browser state.

The maintained baseline and assembled browser scenario pass. Those checks
do not exercise the failure sequences below. This snapshot records defects
and work to address them; it carries no application fixes or hosted changes.

## Invariants

- Every private response and socket operation requires a live session for
  the currently configured numeric owner. OAuth user tokens are transient;
  installation credentials stay in memory, outside durable continuations.
- Complete authoritative reads alone may remove absent PRs. Continuing an
  older logical read must preserve newer observed events and their repair
  work; a success timestamp must not conceal a regression.
- Removing an installation, repository or pending mark must leave the
  scheduler able to process unrelated work and retire orphan progress.
- Monitoring overrides must follow their intended ownership scope. Resetting
  a record after transfer must also reset any durable override that can
  recreate it. Organization repositories remain opt-in.
- Scheduled GitHub sweeps run only while an overview is visible; webhook
  work continues independently. Failed and overdue state stays explicit.
- The browser distinguishes a terminal authorization failure from a
  recoverable transport outage, and source-change notices describe changes
  in GitHub facts rather than the passage of time.
- CLI commands honor exclusions before dispatch, including selected paths
  below a Git root. Read-only commands preserve local repositories; `each`
  passes the owner's literal argv to the selected directory.
- Hosted data describes GitHub evidence. Laptop observations remain local
  and dated; future index/public/LLM designs are not current capabilities.

## Findings

### Open and Moved

- `orphan-reread-continuation-blocks-events` — **An orphan continuation
  permanently blocks later event reads.** Bug · Open · Verified.
  - Where: `src/object/overview-sync.ts:207` (`OverviewSync.alarm`),
    especially the continuation-based filtering at line 210.
  - Severity: P1.
  - A large reread yields a continuation, then its installation disappears.
    The alarm removes its marks but retains `state.reread`; selection now
    considers only the orphan's IDs, so no reread can reach its cleanup.
    Events for other installations stay due indefinitely while alarms keep
    being rearmed, including after object restart. Discard invalid progress
    before selecting jobs and resume unrelated due marks.
  - Evidence: a Workers-runtime reproduction with real object storage
    yielded a continuation for installation 9, removed it, delivered an
    event for accepted installation 20 and ran ten due alarms. No additional
    read occurred; the orphan progress and the new overdue mark persisted.
  - Review backlog: `repair-overview-reread-lifecycle`

- `sweep-continuation-regresses-event-state` — **A continued sweep
  overwrites newer event data and reports success.** Bug · Open · Verified.
  - Where: `src/object/overview-sync.ts:470` (`OverviewSync.sweep`),
    unconditional application at line 473; `applyPr` at line 375 and
    repository reconciliation at line 391.
  - Severity: P1.
  - Continuations replay successful API responses from an earlier logical
    read. An event reread can store a new PR head and clear its mark between
    sweep phases, after which the sweep reapplies its cached old head and
    records success. With no repair mark left, correction waits for the next
    two-minute sweep, breaking the 60-second notified-change bound. Version
    observations or invalidate affected progress before applying/reconciling
    cached responses; cover zero counts and repository reads too.
  - Evidence: a real-storage scheduler reproduction paused a partial sweep,
    processed a webhook reread to `new-head`, then resumed the sweep to
    `old-head`. Marks were empty, the sweep reported success and the next
    sweep was scheduled 120,000 ms after its start. Reader responses were
    controlled contract fixtures; no live GitHub timing is claimed.
  - Review backlog: `protect-overview-read-ordering`

- `sessions-survive-owner-change` — **Old sessions remain authorized
  after the configured owner changes or is removed.** Security · Open · Verified.
  - Where: `src/worker/auth.ts:163` (`findSession`),
    `src/worker/index.ts:15` (session gate), `src/object/schema.ts:22`
    (session records).
  - Severity: P2.
  - Sessions contain a hash and lifetime without an owner identity, and
    lookup checks expiry before the Worker reads configuration. A session
    issued for owner A still passes the gate after `OWNER_ID` becomes B or
    is unset, until its seven-day expiry. Bind sessions to the configured
    owner, reject invalid owner configuration and apply the same check to
    existing sockets.
  - Evidence: two Workers-runtime tests created a session for owner 1001
    and called the real protected `/api/session` route with `OWNER_ID=2002`
    and with no `OWNER_ID`. Both returned 200 and `signedIn: true` using
    real object storage. Configuration was supplied through the existing
    test helper; an actual deployment change was not performed.
  - Review backlog: `bind-sessions-to-configured-owner`

- `transfers-preserve-durable-monitor-override` — **A transferred
  repository inherits its previous monitoring opt-in.** Bug · Open · Verified.
  - Where: `src/object/overview-sync.ts:93` (`receive` transfer reset),
    line 380 (`applyPr` owner-change reset),
    `src/object/repository-selection.ts:123` (override restoration).
  - Severity: P2.
  - Transfer handling clears `RepositoryRecord.monitorOverride` but leaves
    `repository-monitoring:<id>` in settings. Discovery prefers that setting,
    so the same repository ID in another accepted organization becomes
    monitored without a new opt-in. Clear or ownership-scope durable
    overrides whenever transfer detection resets the record, including
    transfers discovered without a delivery.
  - Evidence: real stores and selection received a transfer for an opted-in
    repository in organization installation 9. The record became off/null;
    discovery in installation 20 restored true/monitored from settings.
    GitHub listings and owner permission reads were stubbed.
  - Review backlog: `reset-monitoring-overrides-on-transfer`

- `each-nested-directory-bypasses-remote-exclusion` — **Commands run
  below a repository excluded by its remote.** Bug · Open · Verified.
  - Where: `src/cli/survey.ts:107` (`discoverDirectories` noncheckout
    branch), `src/cli/commands.ts:191` (`each` target selection).
  - Severity: P2.
  - An index `Path` can select an ordinary directory inside a Git checkout.
    Because its physical path differs from the Git root, discovery returns
    it before remote exclusion checks; `each` then dispatches commands there.
    A remote-excluded employer repository is therefore reachable through
    `employer/component`, including with commands that operate on the
    enclosing Git repository. Apply enclosing-repository remote exclusions
    before dispatch without collecting private survey signals.
  - Evidence: a disposable employer repository had a company remote and
    `excludeRemote=*company.example*`; the index named its `component`
    subdirectory. `each -- git rev-parse --show-toplevel` still executed
    and printed the excluded repository root. No destructive command ran.
  - Review backlog: `honor-remote-exclusions-for-nested-each`

- `expired-session-reconnect-loop` — **An ended session is retried
  indefinitely as a connection outage.** Bug · Open · Verified.
  - Where: `src/frontend/overview-client.ts:206` (`socket.onclose`),
    line 279 (browser adapter), `src/frontend/App.tsx:10` (session effect).
  - Severity: P2.
  - Expiry/revocation closes the socket with 1008, `session ended`, but the
    adapter discards the reason and all closes schedule reconnects. The App
    checks `/api/session` only on mount, so later 401 handshakes leave the
    owner looking at a reconnecting page and retained snapshot rather than
    a sign-in explanation. Preserve terminal close information and recheck
    authorization, returning to sign-in on 401; keep ordinary outage backoff.
  - Evidence: the production client with fake sockets received an initial
    snapshot, a terminal close and four failed reconnects: five connections,
    disconnected state and the retained snapshot, with no session-ended
    state. The real server's 1008/401 path was inspected. This was not a
    real-browser expiry reproduction; reload or Sign out recovers manually,
    and server authorization still blocks new access.
  - Review backlog: `recover-overview-after-session-expiry`

- `oauth-callback-unbounded-exchanges` — **Callback attempts reach the
  token endpoint without a per-client limit.** Security · Open · Read.
  - Where: `src/worker/auth.ts:100` (`finishSignIn`).
  - Severity: P2.
  - A client can obtain fresh state and repeatedly reach `exchangeCode`;
    state validation alone does not bound the App's token-request usage.
    The accepted GitHub integration spec requires a limit before exchange
    to reduce owner lockout. The existing `rate-limit-sign-in-callback`
    TODO already specifies bounded counters, independent clients and the
    no-anonymous-durable-rows boundary; retain it rather than duplicate it.
  - Evidence: inspected callback control flow and the existing TODO. No
    quota exhaustion or live OAuth request was attempted, and the remote
    quota cited in the existing design was not freshly measured.
  - Inventory only: covered by existing ready TODO
    `rate-limit-sign-in-callback`.

- `time-only-stale-change-note` — **A time-only stale transition is
  announced as an update on GitHub.** Bug · Open · Verified.
  - Where: `src/frontend/overview-client.ts:61` (`changesBetween`),
    fallback text at line 68.
  - Severity: P3.
  - Comparing entire rows makes a quiet PR crossing seven days appear
    updated on GitHub when only `row.stale` changed. It flashes the row and
    retains that inaccurate notice for two minutes. Compare source facts
    separately from time-derived flags, or label the stale transition
    explicitly.
  - Evidence: production `buildSnapshot` and client processing at one
    millisecond before and exactly at seven days used the identical PR.
    All GitHub facts stayed equal; stale changed false to true and the
    client emitted `Updated on GitHub`.
  - Review backlog: `distinguish-stale-flags-from-github-updates`
