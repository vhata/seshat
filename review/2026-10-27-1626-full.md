## Summary

Four open findings: two P2 and two P3. Three are promoted to separate
review-backlog work; the template contradiction remains inventory.
All eight previous findings are closed after checking current source and
rerunning their scenarios or focused regression tests.

An older installation guard can erase a concurrently discovered and
accepted installation and its cached repositories. Unrelated deliveries
can repeatedly discard progress for a deep PR read. The CLI can record
incorrect branch observations when tags collide with branch names. The
PR template still asks for review history in the squash commit body.

The complete local baseline, assembled browser scenario and offline
recovery checks pass. This review records findings and follow-up work;
it changes no application code or hosted resources.

## Invariants

- Every private response and socket operation requires a live session for
  the current numeric owner. User tokens are transient; installation
  credentials stay outside durable reader progress.
- Only complete authoritative reads may remove absent data. Older reads
  must preserve newer observations, installation acceptance and repair
  work. Ordering protection must also allow continued reads to finish.
- Removing installations, repositories or marks retires orphan progress
  without blocking unrelated jobs. Monitoring overrides follow numeric
  repository ownership; organizations remain opt-in.
- Scheduled sweeps require a visible authorized overview. Webhook work
  continues independently, and failed or overdue state remains explicit.
- The browser distinguishes terminal authorization failure from transport
  outage. Change notices describe source changes, not elapsed time.
- CLI exclusions apply before dispatch, including nested paths. Git child
  processes use the intended repository and stable reference identities.
- Site maintenance preserves its saved target and credentials, isolates
  local validation from account selectors, and verifies release identity.
- Recovery evidence distinguishes synthetic exact-table restoration from
  native hosted recovery. Revoked sessions can reappear after restoration
  and must be invalidated before ordinary access resumes.
- Hosted data describes GitHub evidence. Laptop observations stay local
  and dated. PR descriptions explain lasting behavior; review records
  belong in comments.

## Findings

### Open and Moved

- `stale-installation-guard-removes-newer-installation` — **An older
  installation guard deletes a newer accepted installation.** Bug · Open
  · Verified.
  - Where: `src/object/instance.ts:203` (`checkInstallations`), especially
    the `gone` calculation at line 217 and cleanup at lines 220-226.
  - Severity: P2.
  - An old complete GitHub list is applied against the current stored
    installation set after asynchronous work. If another guard discovers
    an organization meanwhile and the owner accepts it, the old list
    lacks that ID and removes its acceptance, repository rows and PR cache.
    The acceptance-preservation map protects only IDs in the old list.
    Serialize/coalesce reconciliations or reject an obsolete generation
    before destructive reconciliation; retaining every current ID would
    instead conceal real uninstallations.
  - Evidence: in the Workers runtime with real SQLite storage, list A
    returned personal installation 10 plus stranger 30. While A awaited
    uninstalling 30, list B returned 10 plus organization 20; B completed,
    20 was accepted, and its repository was discovered. Completing A then
    left only 10 and no repositories. The coordinator independently reran
    the passing one-test reproduction; cli_review confirmed the source
    and reachable setup, refresh and alarm callers. The probe stubs GitHub
    and suppresses alarm rearming to isolate reconciliation; it does not
    establish live interleaving. No remote installation is deleted by the
    stale cleanup, and durable monitoring overrides were not shown lost.
  - Review backlog: `serialize-installation-guard-reconciliation`

- `unrelated-deliveries-starve-deep-rereads` — **Unrelated webhook traffic
  repeatedly discards a deep PR read's continuation.** Bug · Open · Verified.
  - Where: `src/object/overview-sync.ts:129` (`receive`), line 193
    (`invalidateReads`) and lines 200-205 (`normalizeReread`).
  - Severity: P2.
  - Every delivery on an accepted installation increments its shared read
    generation, even an ordinary edit to another PR. A PR requiring more
    than one bounded read invocation repeatedly restarts while unrelated
    events arrive between invocations. Its data never reaches storage and
    the old deadline can monopolize subsequent rereads. Scope invalidation
    to affected identities or retain unaffected progress while preventing
    older reads from overwriting newer facts.
  - Evidence: the production scheduler and real reader, backed by SQLite,
    read a synthetic PR with 2,100 check contexts across 42 standard
    50-context pages at the normal 40-call invocation cap. One edit on
    another PR every three simulated seconds caused 31 initial reads over
    92 seconds, zero stored PRs and a still-pending original mark. With the
    unrelated traffic stopped, the next alarm completed using identical
    successful API data. The coordinator independently reran the passing
    one-test reproduction. This uses a large synthetic PR, injected token
    issuance and controlled scheduler timing, not a measured live workload.
  - Review backlog: `scope-reread-invalidation-to-affected-prs`

- `survey-ref-abbreviation-ambiguity` — **Colliding tags corrupt branch
  observations in the local survey.** Bug · Open · Verified.
  - Where: `src/cli/survey.ts:222` and line 224 (`signals`); related manual
    examples at `skills/survey-projects/SKILL.md:480` and line 493.
  - Severity: P3.
  - `git symbolic-ref --short` produces an unambiguous abbreviation, not
    a fixed namespace removal. A branch and tag both named `main` produce
    `checkedOut: heads/main`. With default `trunk`, an origin HEAD pointing
    at `refs/remotes/origin/trunk` and tag `origin/trunk`, Git returns
    `remotes/origin/trunk`; the prefix check fails, lists the default as
    nondefault, and emits a false missing-default warning. Read full refs
    and strip the exact expected namespace in code and skill examples.
  - Evidence: disposable repositories kept the same full symbolic refs
    while adding only the colliding tags. Before the remote collision the
    survey reported `branches: feature`; afterwards it reported
    `branches: feature, trunk` and the warning. The coordinator reran both
    failures. No remote calls or repository mutations outside the fixture
    occurred.
  - Review backlog: `use-full-survey-symbolic-refs`

- `pr-template-embeds-review-history` — **The PR template requests
  transient review history in the squash commit body.** Docs · Open · Read.
  - Where: `.github/pull_request_template.md:13` (`## Review`).
  - Severity: P3.
  - The template asks for reviewer identity, reviewed commit, verdict and
    finding dispositions in the PR body, contradicting the contract and
    the owner's future-commit-message rule. Remove this section or replace
    it with an HTML reminder to post the separate review comment. The
    contradiction also existed at the previous reviewed commit.
  - Inventory only: align the project template during workflow maintenance.
    The current upstream template already puts review in a comment, but
    installer `--check` covers Docket and AGENTS rather than this stale
    project template. This low-priority documentation inconsistency does
    not need a separate product fix or a change to installed policy.
